# 平台支持

区分构建目标、宿主实现和实体设备验收。

## 应用可用情况

| 平台 | 当前证据 |
| --- | --- |
| Windows | 已构建桌面应用，并验证过基于 WebView 的插件承载 |
| Android ARM64 | 已构建 APK，原生插件 Activity 与返回接入已编译 |
| Android 兼容环境 | 需要在具体环境中验收，包括卓易通 |
| macOS 与 Linux | 有桌面适配器，本轮流程不代表已有应用分发构建 |
| iOS | 本轮流程未建立安装包或 TestFlight 分发 |

Android 构建成功不代表所有移动系统行为都已验证。
使用交互式跨设备功能时，请保持应用前台。

## 原生能力

| 能力 | 当前边界 |
| --- | --- |
| 鼠标会话接收端 | Windows 原生后端，其他接收端明确拒绝不支持的控制 |
| 桌面 URL、路径、通知与剪贴板操作 | 取决于桌面适配器、已安装工具和系统策略 |
| 移动端执行桌面命令类操作 | 当前命令执行器明确不支持 |
| 文件传输与插件运行时 | 共享核心，并受宿主接入和平台构建要求约束 |
| 移动端后台接收 | 受系统挂起影响，没有持续在线交付保证 |

## 能力检查

插件既需要声明和批准能力，也需要当前宿主有对应实现。
已配对设备和已安装包不会创造平台支持。

页面分别使用 `env.can`、`env.platformSupports` 和 `env.hostSupports` 判断不同条件。
支持检查之后，仍要处理实际执行拒绝。

## 不支持的操作

平台或 API 不支持时，返回结构化拒绝。
不要只让用户重复重试缺失的实现；应选择已支持的接收设备，或采用其他可用插件路径。
